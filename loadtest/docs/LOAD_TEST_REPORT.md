## 3. 시스템 수용 능력 분석

### 3.1 "몇 명까지 버티는가?" — 추정치

| 시나리오 | 동시 사용자 수 | 에러율 | 평가 |
|----------|----------------|--------|------|
| **AI 파싱 없음** (검색·채팅만) | 5명 | 0% | ✅ Baseline에서 검증됨 |
| **AI 파싱 포함** (현재 Load Test) | 25명 | 27% | ❌ 과부하 |
| **AI 파싱 포함** (추정 안정 구간) | **2~4명** | — | VUs 축소 후 재검증 필요 |

### 3.2 근거

1. **Baseline (5 VUs, AI 없음)**
   - 675 요청, 실패 0건, 에러율 0%
   - 현직자 검색 P95: 33ms
   - → AI 파싱을 쓰지 않으면 **5명 동시 접속은 안정**

2. **Load Test (25 VUs, AI 12명)**
   - LLM 파싱 시도 193회 중 성공 **9회 (4.66%)**
   - 실질적으로 AI 파싱은 거의 **1~2명 수준**에서만 성공
   - 12 VUs가 동시에 Gemini를 호출 → rate limit·과부하로 대부분 500 에러

3. **추정**
   - Gemini 무료/제한 플랜 기준: 동시 AI 파싱 **2~4명** 정도가 현실적
   - VUs를 4 이하로 낮추고 재테스트 필요

### 3.3 수용 능력 요약

```
┌─────────────────────────────────────────────────────────────┐
│  동시 사용자 수용 능력 (추정)                                 │
├─────────────────────────────────────────────────────────────┤
│  • AI 파싱 사용자:     2~4명  (현재 Gemini 한도 기준)         │
│  • 일반 사용자(DB):    5명 이상 (Baseline 검증)               │
│  • 혼합(피크):         AI 2~4 + 일반 5~8 ≈ 7~12명            │
└─────────────────────────────────────────────────────────────┘
```

## 5. 오류 원인 분석

### 5.1 오류 유형별 분류

| 오류 유형 | 빈도 | HTTP Status | 원인 |
|-----------|------|-------------|------|
| **LLM 파싱 실패** | 184회 이상 | 500 | AI 서버 / Gemini API 실패 |
| 현직자 검색 실패 | 다수 | 200 | 응답시간 초과 또는 데이터 부재 |
| 메시지 목록 실패 | 다수 | 200 | 응답시간 초과 |
| 채팅방 생성 실패 | 37건 | — | LLM 실패로 이력서 미생성 → 후속 실패 |
| 회원정보 수정 실패 | 8건 | 200 | 응답시간 초과 |

### 5.2 LLM 파싱 500 에러 — 근본 원인

```
부하테스트 → Backend (/api/v1/resumes/tasks) → AI 서버 → Gemini API
                                                    ↓
                                            500 에러 다수 발생
```

**가능성 높은 원인 (우선순위 순)**

| 순위 | 원인 | 근거 |
|------|------|------|
| **1** | **Gemini API Rate Limit (429)** | 12 VUs 동시 LLM 호출, 성공률 4.66% → 동시 요청 과다 |
| **2** | **Gemini 서버 과부하 (503)** | P95 21초 → 대기·재시도로 인한 지연 |
| **3** | AI 서버 ↔ Backend 통신 오류 | dev 환경 네트워크/설정 이슈 가능 |
| **4** | PDF 다운로드/파싱 실패 | S3 Presigned URL 만료, 이미지 PDF 등 |

### 5.3 연쇄 실패 흐름

```
[Group A: AI 파싱 유저]
     │
     ▼
  LLM 파싱 500 에러  ←── 핵심 원인
     │
     ├─→ 이력서 미저장
     │       │
     │       ├─→ 현직자 검색 시 이력서 없음 → 비정상 응답
     │       ├─→ 채팅방 생성 실패 (37건)
     │       └─→ 메시지 목록 조회 실패
     │
     └─→ 다른 Group(B, C)에도 간접 영향 (DB/API 공유)
```

### 5.4 "Status: 200"인데 실패로 표시되는 이유

- `현직자 검색 실패 | Status: 200` 등은 **HTTP 200**이지만:
  - **응답시간 > 3초**로 check 실패
  - 또는 **응답 body**가 비어 있거나 비정상 (LLM 실패로 이력서 없음)
- config에서 `check()` 기준을 통과하지 못해 실패로 집계됨.

## 6. 권장 조치사항

### 6.1 단기 (즉시 적용 가능)

| # | 조치 | 예상 효과 |
|---|------|-----------|
| 1 | **Group A VUs 12 → 4로 감소** | 동시 LLM 호출 감소, rate limit 완화 |
| 2 | **dev 서버 로그 확인** | `[RESUME_PARSE]`, `429`, `503` 등 실제 에러 원인 확인 |
| 3 | **config.js printMetric 수정** | `p(99)` undefined 시 TypeError 방지 |

### 6.2 중기 (인프라/설정 변경)

| # | 조치 | 예상 효과 |
|---|------|-----------|
| 1 | **Gemini 유료 플랜 또는 할당량 점검** | RPM 상향, 안정적인 AI 파싱 |
| 2 | **AI 파싱 비동기(Async) 도입** | 동기 대기 감소, 큐 기반 처리 |
| 3 | **부하 분산** | AI 파싱 시나리오 비중 축소 (예: 40% → 20%) |

### 6.3 장기 (아키텍처)

| # | 조치 | 예상 효과 |
|---|------|-----------|
| 1 | **AI 파싱 큐(Queue) 도입** | 동시 LLM 호출 제어, 재시도 정책 적용 |
| 2 | **Circuit Breaker** | 연속 실패 시 일시적 요청 중단으로 연쇄 실패 방지 |
| 3 | **Fallback 제공** | LLM 실패 시 수동 입력 등 대안 플로우 |
