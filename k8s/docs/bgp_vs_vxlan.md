# BGP vs VXLAN — CNI 네트워킹 모드 비교

> 쿠버네티스 CNI가 노드 간 Pod 통신을 구현하는 두 가지 방식(BGP, VXLAN)을 비교하고,
> AWS 환경에서의 호환성을 정리합니다.

---

## 1. 왜 이 선택이 필요한가

쿠버네티스에서 각 Pod는 고유한 IP를 받습니다:

```
[Worker 노드 1] (호스트 IP: 10.0.1.10)
  ├── BE Pod     → Pod IP: 10.244.1.5
  └── Redis Pod  → Pod IP: 10.244.1.8

[Worker 노드 2] (호스트 IP: 10.0.2.20)
  ├── BE Pod     → Pod IP: 10.244.2.3
  └── AI Pod     → Pod IP: 10.244.2.7
```

**문제**: 노드 1의 BE Pod(10.244.1.5)가 노드 2의 AI Pod(10.244.2.7)에 통신하고 싶을 때, **노드 간 물리 네트워크는 Pod IP(10.244.x.x)를 모릅니다.** 물리 네트워크는 호스트 IP(10.0.x.x)만 알고 있습니다.

→ CNI는 이 **"노드 간 Pod IP 통신"**을 해결해야 합니다. 방법이 크게 두 가지: **VXLAN(오버레이)**과 **BGP(라우팅)**.

---

## 2. VXLAN (오버레이 방식) — "택배 포장"

### 동작 원리

Pod 패킷을 **한 번 더 감싸서(캡슐화)** 보냅니다:

```
[노드 1] BE Pod → AI Pod(노드 2)로 패킷 보내고 싶음

① 원본 패킷:  src: 10.244.1.5 → dst: 10.244.2.7  (Pod IP)
② VXLAN 캡슐화: 원본 패킷을 통째로 감싸서 새 헤더 붙임
   외부 헤더:   src: 10.0.1.10 → dst: 10.0.2.20   (호스트 IP)
   내부:        [원본 Pod 패킷]
③ 호스트 네트워크가 외부 헤더(10.0.x.x)만 보고 노드 2로 전달
④ 노드 2에서 외부 헤더 벗기고 → 원본 패킷을 AI Pod에 전달
```

### 비유: 택배 포장

- 편지(Pod 패킷)에 적힌 주소(Pod IP)를 택배 회사가 모름
- 편지를 박스에 넣고, 박스에 택배 회사가 아는 주소(호스트 IP)를 적음
- 택배 회사는 박스 주소만 보고 배달 → 도착하면 박스 열어서 편지 전달

### 장단점

| 장점 | 단점 |
|:-----|:-----|
| 물리 네트워크(AWS VPC, 라우터 등)가 **Pod IP를 전혀 몰라도 됨** | 캡슐화/역캡슐화 처리 비용 |
| 어떤 환경에서든 **즉시 동작** | **레이턴시 ~0.5ms 추가** |
| 네트워크 설정 변경 불필요 | 패킷 크기 약 50바이트 증가 (MTU 오버헤드) |

---

## 3. BGP (라우팅 방식) — "도로에 이정표 세우기"

### 동작 원리

Pod IP 대역을 **물리 네트워크의 라우팅 테이블에 직접 등록**합니다:

```
[노드 1] BE Pod → AI Pod(노드 2)로 패킷 보내고 싶음

사전 준비: 라우팅 테이블에 이렇게 등록해둠
  "10.244.1.0/24 → 노드 1 (10.0.1.10)으로 보내라"
  "10.244.2.0/24 → 노드 2 (10.0.2.20)로 보내라"

① 원본 패킷:  src: 10.244.1.5 → dst: 10.244.2.7  (Pod IP 그대로!)
② 라우터가 라우팅 테이블 참조 → "10.244.2.x는 노드 2로 가면 되겠구나"
③ 캡슐화 없이 원본 패킷 그대로 노드 2에 전달
④ 노드 2가 Pod에 직접 전달
```

### 비유: 도로에 이정표 세우기

- "Pod IP 10.244.1.x 방면 → 노드 1 방향"이라는 이정표를 라우터에 설치
- 패킷이 이정표를 따라 직접 목적지에 도착
- 박스 포장(캡슐화)이 필요 없음

### 장단점

| 장점 | 단점 |
|:-----|:-----|
| 캡슐화 없음 → **네이티브 성능** | **라우터/네트워크가 Pod IP 대역을 알아야 함** |
| 레이턴시 추가 없음 | 라우팅 테이블에 등록 필요 |
| MTU 오버헤드 없음 | 노드 추가/삭제 시 라우팅 테이블 동기화 필요 |

---

## 4. 한눈에 비교

| | VXLAN (오버레이) | BGP (라우팅) |
|:--|:---------------|:-----------|
| **동작 방식** | 패킷을 감싸서 호스트 IP로 전달 | 라우팅 테이블에 Pod IP 등록 |
| **물리 네트워크 변경** | ❌ 불필요 | ✅ 라우팅 테이블 수정 필요 |
| **성능** | 캡슐화 오버헤드 (~0.5ms) | 네이티브 성능 |
| **설정 복잡도** | 낮음 (어디서든 즉시 동작) | 높음 (라우팅 연동 필요) |
| **적합한 환경** | 클라우드, 소규모 클러스터 | 온프레미스, 대규모 클러스터 |

---

## 5. BGP는 AWS에서 호환되는가?

### 결론: "되긴 되지만, kubeadm에서는 매우 까다롭다"

AWS VPC에서 BGP를 사용하려면 **VPC 라우팅 테이블에 Pod CIDR을 등록**해야 합니다.

### AWS VPC 라우팅 테이블의 구조

```
AWS VPC 라우팅 테이블 (기본):
  10.0.0.0/16  → local (VPC 내부)
  0.0.0.0/0    → Internet Gateway

BGP 사용 시 추가해야 하는 항목:
  10.244.1.0/24 → eni-xxxx (노드 1의 ENI)    ← 수동 추가
  10.244.2.0/24 → eni-yyyy (노드 2의 ENI)    ← 수동 추가
  10.244.3.0/24 → eni-zzzz (노드 3의 ENI)    ← 노드 추가 시 또 추가
```

### 문제가 되는 이유

| 문제 | 설명 |
|:-----|:-----|
| **① AWS VPC는 동적 BGP를 지원하지 않음** | 온프레미스 라우터는 BGP 프로토콜로 "나한테 이 대역이 있어"라고 자동 알림(BGP Peering). **AWS VPC 라우터는 BGP Peering을 지원하지 않음.** 각 노드의 Pod CIDR을 AWS API로 **수동 등록**해야 함 |
| **② 노드 추가/삭제 시 동기화** | HPA로 노드가 추가되면 새 Pod CIDR을 라우팅 테이블에 등록하고, 노드 삭제 시 제거해야 함. 자동화하려면 **별도 컨트롤러 개발** 필요 |
| **③ 라우팅 테이블 항목 제한** | AWS VPC 라우팅 테이블은 기본 **50개 항목까지** (확장 요청 시 최대 1,000개). 소규모에서는 문제없지만 제한 존재 |
| **④ Source/Dest Check 비활성화** | AWS EC2는 기본적으로 자기 IP가 아닌 패킷을 버림. Pod IP로 오는 패킷을 받으려면 **각 인스턴스의 Source/Dest Check를 비활성화**해야 함 |

### EKS vs kubeadm에서의 차이

| 환경 | BGP/라우팅 사용 가능성 | 구현 방식 |
|:-----|:-----------------|:---------|
| **EKS** | ✅ 쉬움 | AWS VPC CNI가 자동으로 ENI에 Pod IP를 할당하고 라우팅 처리. BGP가 아니라 **ENI 기반 네이티브 라우팅**이므로 수동 설정 불필요 |
| **kubeadm** | ⚠️ 가능하나 까다로움 | ① 각 노드에서 Source/Dest Check 비활성화 (AWS API 호출) ② 각 노드의 Pod CIDR을 VPC 라우팅 테이블에 수동 등록 (또는 자동화 스크립트 개발) ③ 노드 증감 시 라우팅 테이블 동기화 필요 |

> **참고**: EKS에서 "라우팅이 쉽다"고 하는 것은 BGP를 쓰는 것이 아니라, **AWS VPC CNI가 EC2의 ENI(Elastic Network Interface)에 직접 Pod IP를 부착**하는 방식입니다. VPC 네트워크가 Pod IP를 네이티브로 인식하므로 캡슐화도, BGP도 필요 없습니다. 이 방식은 EKS 전용이며 kubeadm에서는 사용할 수 없습니다.

## 6. Re-Fit에서 VXLAN을 선택한 이유

```
BGP의 이점: 캡슐화 없는 네이티브 성능 (~0.5ms 절약)

BGP의 비용: VPC 라우팅 테이블 수동 관리
            + Source/Dest Check 비활성화
            + 노드 증감 시 동기화 자동화 개발

Re-Fit 환경: 
  - kubeadm 자체 구축 (EKS의 자동 라우팅 사용 불가)
  - Worker 2~3대, Pod ~20개의 소규모 클러스터
  - 내부 트래픽(BE↔Redis, BE↔Kafka)은 동일/인접 노드 간 통신이 대부분
  - 0.5ms 레이턴시 차이가 서비스 품질에 영향을 미치지 않는 규모
```

→ **성능 이점(~0.5ms)이 운영 비용(라우팅 관리)을 정당화하지 못함** → VXLAN 선택

### BGP가 합리적인 경우

| 환경 | 이유 |
|:-----|:-----|
| **대규모 클러스터** (노드 100대 이상) | VXLAN 캡슐화 오버헤드가 대량 트래픽에서 누적. 노드 간 통신이 빈번하고 레이턴시에 민감 |
| **온프레미스 환경** | 물리 라우터와 BGP Peering이 가능. 네트워크 팀이 라우팅 테이블을 관리 |
| **EKS** | AWS VPC CNI가 ENI 기반 네이티브 라우팅을 자동 처리. BGP 자체를 쓸 필요 없이 동등한 성능을 얻음 |
| **고성능 요구** | 지연시간에 극도로 민감한 워크로드 (금융 거래 시스템, 실시간 게임 서버 등) |
